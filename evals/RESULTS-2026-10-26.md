# Scenario results, 2026-10-26

Supersedes `RESULTS-2026-10-25.md`, which measured the Phase 1 skill (six scenarios, kept as history).

This is a first signal from synthetic scenarios, not a benchmark. Read the limits below before the numbers.

## Setup

- `claude plugin eval` on Claude Code 2.1.278, Fedora Linux, OS sandbox. Agent model: Claude Code's default at the time (`claude-sonnet-5`). Judge for `llm` graders: `haiku`, three votes.
- Two arms per scenario: **with** the plugin and **without** it. Two or three runs per arm. Each run is isolated (no user settings, memory or other plugins) and the prompts do not name the skill.
- Scores are the fraction of that scenario's graders that passed, averaged over runs. Cost is the tool's list-price estimate per run (the runs used the maintainer's Claude plan, not an API bill).
- S9, S10 and S11 vendor sqlglot into the workspace because the sandbox does not see the host's Python packages. S1–S8 and S12–S13 run without sqlglot, which is also what S2 tests.

## What the numbers say

**Where the skill changes behavior (differences large enough to be unlikely noise at this sample size):**
- It names a missing tool and labels a hand-made translation as unverified (S2: 1.00 against 0.00).
- It backs up before editing and says where (S5: 1.00 against 0.25).
- It computes the waterfall with the script, reports the residual against the Spec's tolerance, and leaves business questions to an approver (S6: 1.00 against 0.50).
- It asks instead of choosing between two definitions of a business rule (S1: 1.00 against 0.60).
- It applies a rule approved in `tieout/rules.local.md` and keeps an unapproved one as an assumption, in one of two runs (S12).

**Where it does not help, or hurts:**
- S7: both arms noticed the missing column; no difference.
- S13 (read-only investigation): the skill was available but the agent did not invoke it in either run, and even recommended it in its answer. The skill's description has since been changed to name read-only investigation; that change was **not measured**.
- S11 (drop a column): the lowest with-skill score. With the skill, both runs ran the impact scan and said which file could not be analyzed, but the grader for a staged plan with a way back for each step failed in all four runs, with and without the skill. I did not read those plans to find out whether the agent or the judge was at fault.
- S8 cost the same with and without the skill, and S4 differs little: the agent without the skill already finds the technical causes. What the skill adds is process, not detection of the underlying defect.

**Process changes cost more tokens.** The extra cost is mostly turns spent writing files and following the cycle.

## Limits you should weigh

1. **Small samples.** Two or three runs per arm. A single run moves a score by 0.25–0.5.
2. **One model, one agent.** Not run on smaller models or other agents.
3. **The scenarios and the skill were tuned together.** After each measurement I changed the skill in response to failures and, in several cases, the graders. Grader changes made after seeing results: S1 regex (ignores comments), S3 (language check, likelihood-language check, queries-in-reply check), S4 (accepts "file not modified"), S6 (accepts rounding measured as an effect, and a conclusion grounded in the Spec), S8 (two graders). Scores before and after those changes are not comparable. The risk of fitting the skill to its own tests is real; only use on real work shows whether it holds.
4. **Different batches.** S1, S2, S4–S9 and S11 ran at commit `6a2d397`; S3, S10, S12, S13 ran after the change that removed files in code-only mode (`2faf1c2`). The later description change and the reworded S12 rule were not measured.
5. **Two measurement runs were cut off by the plan's session limit.** Their results were discarded; only complete runs are in the table.
6. **Judge noise.** `llm` graders use a small judge model. Several failures were judge errors that were then replaced by regex checks.
7. **Synthetic data only.** Nothing here was run on real Power BI, Tableau or warehouse data.

## What failed and what is still weak

- S3 code-only analysis went from 0.50 to 0.83 only after two rules changed: the SQL must be in the reply, and no files are created in that mode. Before that, three consecutive runs left the SQL in a file despite explicit instructions.
- S11: the staged plan with a way back per step did not pass the grader in any run. Unknown whether the plans were weak or the judge too strict.
- S13: activation on read-only prompts (see above).
- S12: one run decided the whole definition was pending because of the unapproved second rule instead of applying the approved first rule; the fixture wording was ambiguous and has since been fixed.
